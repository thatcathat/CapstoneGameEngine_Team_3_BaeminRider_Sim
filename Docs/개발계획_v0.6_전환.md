# 배달 시뮬레이터 v0.6 전환 개발계획

- 작성일: 2026-10-13
- 상태: 개발계획 초안. 이번 작업은 계획 작성이며 게임 구현과 기존 확정 규칙은 변경하지 않는다.
- 목표: 현재 Unity 배달 프로토타입을 바탕으로, 과장된 물리와 연쇄 돌발상황이 있는 반복 배달 게임을 단계적으로 만든다.
- 기준 자료: 현재 프로젝트 규칙·프로토타입 기획서, 사용자 제공 시스템기획 v0.6 PDF·v5.2 HTML 체험판·트리거 수 표·배치 이미지 3장·실행 안내.
- 구분: **문서상 확정**은 첨부 문서에 확정으로 기록된 방향이다. **개발 제안**은 이 계획의 구현 순서·범위다. **시험값**은 체험판의 조정값이다. 문서상 확정을 이번 대화에서 새로 승인된 구현으로 간주하지 않는다.
- 후속 요청 반영(2026-10-13): 사용자가 HTML식 사고 발생 방식으로 전환하는 방안을 계획에 추가하도록 요청했다. 구체적인 전환은 4단계 상세안에 기록한다. 이번 수정은 계획 반영이며 기존 Zone·씬·사건 코드는 변경하지 않는다. 타이머·전달 방식·이동 장비 등 다른 전환 항목까지 승인된 것으로 확대 해석하지 않는다.

## 1. 현재 출발점

현재 구현에는 도보·3인칭 카메라, 음식점 3곳·고객 3명·주문 경로 6개, 후보 3개, 지도·목적지 표시, 두 타이머, 충돌 전달, 정시·지각 보상, 마지막 주문 마무리와 정산이 있다. 사고 2구역·도난 3구역과 추격 회수·재수령, 시간형 사건도 연결되어 있다.

현재 Map 프리팹과 GameScene 배치를 활용한다. 주먹·점프·인라인, 구역 순환 주문, 연쇄 사건, 일차별 고정 사건, 생활비·빚·구매·저장·엔딩은 개발 대상이다. 플레이 검증 상태는 기존 안내 문서를 따르며, 파일과 코드가 있다는 이유로 플레이 검증 완료로 표시하지 않는다.

기존 제작 워크스루에는 일부 이전 사건 규칙과 다음 작업 순서가 남아 있다. 전환 구현 시 관련 기획·규칙·안내를 함께 정리해 서로 다른 기준이 동시에 남지 않게 한다.

## 2. 전환 방향과 결정 항목

### 새 문서에서 확정으로 기록된 방향

- 배달 제한시간은 음식 수령 시 시작한다. 수령 중에는 하루 시간만 흐른다.
- 고객을 주먹으로 쳐서 전달하고, 완료 후 콜 화면은 1번으로 직접 연다.
- 현재 구역에서 수령해 다른 구역으로 배달하고, 도착한 구역에서 다음 콜을 받는다.
- 하루 시간은 숫자 대신 해시계로 표시한다. 영업 종료 후 진행 중인 콜을 마무리한다.
- 자전거 대신 인라인을 구매한다. 인라인을 구매해도 주문 제한시간은 늘리지 않는다.
- 사건을 항상 배치된 오브젝트, 콜마다 활성화하는 트리거, 일차·시각에 따른 고정 사건으로 구분한다.
- 피해는 주로 시간 손해이며, 장애물이 이동 이득도 줄 수 있는 과장된 물리를 지향한다.
- 생활비 차감 후 선택 구매를 하고, 빚 전액을 모으면 일괄 상환·엔딩으로 진행한다.

## 3. 개발 순서

| 단계 | 개발 묶음 | 사용자가 확인할 결과 | 선행 조건 |
|---|---|---|---|
| 1 | 배달·시간·콜 흐름 전환 | 수령 후 타이머, 수동 콜 확인, 마지막 주문 정산 | 전환 규칙 정리 |
| 2 | 주먹·점프·과장 물리 | 고객 펀치 전달, 날아감·착지·복귀 | 1 |
| 3 | 4구역 주문·지도 | 현재 구역 수령 → 다른 구역 전달 → 다음 콜 | 1·2 |
| 4 | 오브젝트·트리거·연쇄 | 소수의 대표 사건을 엮은 짧은 배달 | 2·3 |
| 5 | 골목과 배치 확장 | 큰길과 위험한 지름길을 고르는 배달 | 3·4 |
| 6 | 일차별 고정 사건 | 트럭 사건의 전조·진행·종료가 있는 하루 | 4·5, 최소 일차 관리 |
| 7 | 콜 상황·긴 사건 확장 | 주소 변경, 고양이 대결, 근육맨 동행 등 | 3·4, 종류 선정 |
| 8 | 인라인·경제·저장·엔딩 | 여러 날 배달해 구매하고 빚을 갚는 흐름 | 1·3, 최소 일차 관리 |
| 9 | 표현·밸런스·배포 | 처음부터 엔딩까지 가능한 실행 빌드 | 1~8 |

순서는 우선순위다. 6·7단계의 모든 콘텐츠를 채워야 8단계를 시작할 수 있는 것은 아니다. 대표 사건과 하루 흐름이 안정되면 경제를 연결해 전체 반복을 먼저 완성한다. 날짜별 일정은 범위 결정과 첫 두 단계의 실제 작업량 확인 후 산정한다.

### 1단계: 배달·시간·콜 흐름 전환

**작업**

- `DeliverySession`의 주문 수락과 배달 타이머 시작을 분리한다. 음식 수령 전에는 배달 남은 시간 대신 수령 목표를 표시한다.
- 현재 주문 없음·수령 전·운반 중·완료 상태와 보상 담당 구조를 유지한다. 한 번만 완료·지급하는 방어도 유지한다.
- 완료 후 콜 UI 자동 열기를 제거하고 1번 입력으로 연다. 지도와 콜 UI의 입력·시간 정책을 구분한다.
- 하루 표시를 해시계로 바꾸고 수령 전 주문을 포함한 마지막 주문 마무리를 보존한다.
- 하루 길이와 후보 수는 설정으로 둔다. 600초·후보 2개는 체험판 시작값이며 확정 밸런스로 기록하지 않는다.

**완료 기준**: 수락 후 수령하러 가는 동안 주문 제한시간이 줄지 않는다. 음식 수령 후부터 진행한다. 콜 선택·지도·일시정지의 시간이 정의대로 움직이고, 마감 경계에서 새 주문이나 중복 정산이 발생하지 않는다.

### 2단계: 주먹 전달과 이동 반응

**작업**

- New Input System에 주먹(F·클릭)과 점프를 연결한다. 메뉴 입력과 공격 입력이 충돌하지 않게 한다.
- 전방·거리·방향을 기준으로 타격 대상을 판정한다. 음식 보유와 해당 고객 여부를 확인한 뒤 전달을 요청한다.
- `DeliveryResident`의 일반 접촉 완료를 주먹 전달로 전환한다. 고객 날아감과 보상 처리는 별도로 관리한다.
- 사고 반응을 발사·착지·회복으로 확장한다. 먼저 단순 캐릭터로 구현하고 전신 래그돌은 필요가 확인될 때 검토한다.
- 빠른 이동과 발사 중 벽 관통, 음식·고객 이탈, 조작 잠김에 복구 경로를 둔다. 타이머와 주문 상태는 복구로 초기화하지 않는다.
- 소리 지르기는 오리·닭 등 반응 대상 구현에 맞춰 4단계에서 추가한다.

**완료 기준**: 잘못된 주민·음식 없는 타격은 완료되지 않는다. 고객 주먹 전달은 한 번만 지급된다. 날아간 고객의 연출을 볼 수 있고, 플레이어는 착지·복귀 후 같은 주문을 이어 간다.

### 3단계: 구역 순환 주문과 지도

**작업**

- 현재 Map에서 접근 가능한 구역을 먼저 정의하고, 음식점·배달지를 구역 데이터에 연결한다.
- 현재 구역의 음식점과 다른 구역의 고객으로 주문을 만든다. 도착한 구역이 다음 주문의 출발 구역이 된다.
- 현재 위치가 아니라 마지막 배달 구역으로 콜을 고정할지, 구역 이동 시 새로 판정할지 명시한다. 체험판 방식과 문구의 차이를 확인한다.
- 시작용 일차·다음 날 진행 정보를 준비한다. 경제와 저장은 8단계에 연결한다.
- 최소 도로 연결 정보로 경로 거리를 산출한다. 경로를 만들기 전에는 임의의 직선 거리를 도로 거리라고 표시하지 않는다.
- 큰길 거리 기반 제한시간·보상 등급과 구역 표시를 연결한다. 기존 6개 주문 자산은 참조를 확인하며 시험용으로 보존한다.

**완료 기준**: 현재 구역 수령·다른 구역 배달이 반복되고, 도보로 모든 수령·배달 지점에 접근할 수 있다. 고객·주문·지도 표시가 일치한다. 방금 떠난 구역 제외는 시험 옵션으로 취급한다.

### 4단계: 사건 분류와 대표 연쇄

**첫 콘텐츠 묶음 제안**: 먼저 열리는 문·굴러오는 타이어로 발동과 피격 분리를 확인한다. 다음으로 터지는 맨홀·수박 좌판의 연쇄, 기존 도난 1종을 전환하고 소화전·오리·닭을 확장한다. 이 목록은 대표 개발 범위이며 전체 종류 확정이 아니다.

**작업**

- 오브젝트는 배치된 위치에서 접촉에 반응한다. 트리거는 콜 수락 시 해금·경로·종류 조건으로 활성화하고, 음식 수령 이후 작동한다.
- 기존 `TimedIncidentScheduler`의 주기 추첨 역할을 새 발생 방식으로 대체한다. 구형 씬 연결은 확인한 뒤 에디터에서 전환한다.
- 현재 `IncidentDirector`는 새 사건 시작 시 기존 사건을 정리하므로, 이 구조를 그대로 사용하면 동시 연쇄가 끊긴다. 단발 물리 효과는 각 오브젝트가 실행하고, 추격·붙잡힘처럼 지속되는 행동은 필요한 범위에서 수명을 따로 관리한다.
- 조작 불가·기절·추격이 겹칠 때 하나가 끝나면서 다른 효과까지 해제되지 않게 종료 책임을 정한다. 범용 프레임워크는 먼저 만들지 않는다.
- 맨홀 → 수박 → 다음 함정처럼 작은 연쇄 배치를 만든다. 콤보 활성화가 목표 활성 수를 넘을 수 있는지 정책을 정한다.
- 기존 도난 복구를 유지한 채 새 사건 체계에 맞춘다. 음식 낙하·비둘기·복제 라이더는 분실 의미를 정리한 뒤 추가한다.
- 소리 지르기와 최소 효과음·예고를 연결해 피하기·흩어지기 반응을 확인할 수 있게 한다.

**완료 기준**: 수령 전에는 배치된 고정 오브젝트가 작동하고, 배달 중 전용으로 지정한 일반 트리거는 피격을 발생시키지 않는다. 상시 교통·특수 장치·고정 사건은 각자의 조건을 적용한다. 주문 전환·정산·씬 종료에 지정된 수명 정책대로 정리하되, 진행 중 음식 회수 경로를 잃지 않는다. 회피와 연쇄 중에도 주문 완료가 가능하다.

#### 4-A. HTML식 사고 발생 구조로 전환

**목표 흐름**: 배치·활성 여부 결정 → 접근으로 행동 시작 → 예고·이동·공격 → 실제 접촉 또는 공격 범위 검사 → 피격 반응 → 종료·재사용 관리.

현재 `IncidentTrigger`는 플레이어의 BoxCollider 진입으로 사건을 선택한다. `CrashIncidentActor`는 0.8초 경고 후 위치나 실제 충돌을 재확인하지 않고 `BeginCrash()`를 호출한다. 새 구조에서는 Zone 진입이 위험 요소의 행동을 시작하며, 피격은 각 위험 요소가 따로 판정한다. 경고 중 피했으면 맞지 않아야 한다. 밟는 맨홀처럼 접촉 즉시 작동하는 종류는 접촉 자체를 발동·피격 조건으로 둔다.

| 구분 | 배치·활성 | 행동과 피격 | 종료·재사용 계획 |
|---|---|---|---|
| 고정 오브젝트 | 일차별 배치 대상이면 월드에 존재. 콜 추첨과 분리 | 문짝 접촉, 맨홀 밟기, 수박 접촉 등 개별 판정. 수령 전에도 작동 가능 | 종류별 1회 사용 또는 재장전. 그날 배치 여부와 사용 여부를 별도로 보관 |
| 콜별 일반 트리거 | 수락 시 해금·경로·종류·묶음 조건으로 활성화 | 접근 후 타이어 굴림·동물 추격 등을 시작. 기본 피격 조건은 수령 후 배달 단계이며 일부 대기 동작은 수령 전에도 표시 | 사용 완료·행동 시간 초과·다음 콜 전환을 구분 |
| 일차별 고정 사건 | 날짜·경과 시간·배달 상태로 시작 | 전조 후 트럭·가구 등 개별 위험 요소가 피격 판정 | 목표 달성 또는 시간 종료 시 자신이 만든 요소만 정리 |
| 일반 교통 | 교통 경로에 상시 배치 | 현재 `TrafficVehicle`의 실제 접촉 방식을 활용. 일반 차량은 감속·정지하며 폭주 사건과 구분 | 사건 추첨·콤보 추가 활성화 대상에서 제외 |

HTML의 거리·선분 판정을 Unity의 물리 단위로 그대로 복사하지 않는다. 형상·높이·고속 이동을 고려해 Collider, 이동 구간 검사 또는 공격 범위 검사를 종류에 맞게 선택한다. 감지 영역은 넓게 둘 수 있지만 피격 영역은 실제 문짝·타이어·분출구와 일치시킨다. 빠르게 움직이는 물체가 한 물리 프레임 사이에 플레이어를 통과하지 않는지도 확인한다.

#### 4-B. 기존 구성의 변경 책임

- `IncidentTrigger`: 대상 감지와 행동 시작 요청을 담당하도록 전환한다. 진입 자체가 충격·음식 분실을 확정하지 않게 한다. 배치된 자리, 콜 활성 상태, 행동 중 상태를 구분하고, 이미 행동 중인 대상에 재진입해 중복 생성하지 않는다.
- 사건 설정 자산: 감지 거리, 예고 시간, 이동 속도, 공격 범위, 충격, 사용·재장전 정책, 해금·배달 단계 조건을 보관한다. 현재 사용 완료 여부·경과 시간·대상 참조는 실행 객체에 둔다.
- 개별 Actor: 자신의 예고·이동·접촉·종료를 담당한다. 문은 열리는 문짝, 타이어는 굴러가는 차체, 낙하물은 예고된 착지 지점에서 피격을 판정한다.
- `IncidentDirector`: 새 사건마다 모든 이전 사건을 취소하는 단일 슬롯 제약을 단계적으로 없앤다. 시작 조건·등록·전체 정리는 공통으로 관리하고, 개별 사건의 종료는 해당 사건에만 적용한다. 붙잡힘·흡입 이동처럼 동시에 수행할 수 없는 행동만 충돌 정책으로 조정한다.
- `RiderMotor`: 여러 위험 요소가 공유할 피격 요청과 발사·미끄러짐·기절·착지 상태를 정리한다. 입력 가능 여부와 피격 가능 여부를 분리한다. 현재 `IsRecovering`에 대한 일괄 피격 거부만으로는 HTML의 낮은 비행 중 연쇄를 구현할 수 없다.
- `TimedIncidentScheduler`: 새 콜별 활성화와 일차별 사건 시작에 해당 역할을 이관한다. 전환된 자리에서 구형 스케줄러와 새 활성화가 동시에 호출되지 않게 한다. 미전환 원본 씬의 연결은 유지한다.
- 도난: 추격형은 접근·탈취 판정이 성공한 순간에만 음식 상태를 바꾸는 방향으로 전환한다. 원거리 탈취 종류는 자기 공격 조건을 명시한다. 단일 음식 소유·회수·재수령 처리는 `DeliverySession`이 유지하고, 단순 교통사고나 다른 Actor의 종료가 도둑을 삭제하지 않게 한다.

기존 프리팹과 설정을 한 번에 덮어쓰지 않는다. 대표 새 Actor와 별도 시범 배치를 만든 뒤 전환한 자리만 새 동작으로 연결한다. 같은 자리에서 구형 강제 충격과 새 접촉 충격이 중복 실행되지 않아야 한다. 범용 상태 프레임워크를 먼저 만들지 않고 실제 대표 사건에 필요한 공통 처리부터 추출한다.

#### 4-C. 재사용·동시 사건·연쇄 정책

다음은 HTML에서 확인한 참고 동작과 Unity 적용 제안이다. 숫자는 확정 난이도가 아니다.

| 항목 | HTML 참고 | 적용 계획 |
|---|---|---|
| 콜 활성 수 | 일차별 목표 5/8/10/13. 묶음 활성화로 목표 초과 가능 | 목표 수와 실제 활성 수를 구분하고 기록. 묶음으로 인한 초과 허용량은 설정으로 제한하는 안부터 검토 |
| 경로 주변 선택 | 목표의 약 70%를 예상 경로 7m 주변에서 선택하도록 시도 | 실제 도로 경로를 확보한 뒤 적용. 후보 부족·종류 배분 때문에 정확히 70%가 보장되는 규칙으로 취급하지 않음 |
| 재장전 | 코드상 터지는 맨홀만 10초 경과 및 플레이어 거리 4m 초과 시 재장전. 다른 고정 오브젝트는 대체로 콜마다 1회 | 종류별 정책으로 분리. 문까지 무조건 10초 재장전하는 것으로 해석하지 않음 |
| 연쇄 기록 | 피격 간격 8초 이내면 연쇄 수 증가 | 실제 피격 확정 시에만 집계. 행동 시작·헛친 공격은 집계하지 않음 |
| 추가 활성화 | 피격 시 40m 안의 비활성 일반 트리거를 확률적으로 활성화. 참고 확률은 오브젝트 30%, 그 외 80% | 고정된 2개 연쇄가 안정된 뒤 도입. 활성 수 상한·해금·사용 완료·접근 가능성 필터 적용 |
| 공중 연쇄 | 낮은 사고 비행·미끄러짐·일부 착지에서 추가 피격 허용. 일반 점프·안전 발사 등에 예외 존재 | 절대 월드 Y 대신 해당 지면에서의 높이와 이동 상태로 판정. 높이·재피격 간격은 Unity 체감에 맞게 조정 |

- HTML은 여러 위험 요소가 함께 움직이지만 플레이어 행동 상태는 하나로 관리한다. Unity에서도 효과를 무제한으로 더하지 않고, 새 발사가 기존 비행 속도를 대체할지·일부 더할지 종류별로 정한다.
- 같은 공격의 여러 Collider 또는 지속 접촉으로 매 프레임 다시 맞지 않게 한다. 동일 공격의 중복 방지와 다른 위험 요소로 이어지는 연쇄 허용을 구분한다.
- 단순 충격·미끄러짐과 도둑의 도주는 함께 진행 가능하게 한다. 붙잡힘·흡입 이동은 초기안에서 상호 배타적으로 두고, 종료할 때 자신이 건 이동 제한만 해제한다.
- 주문 완료만으로 회수 중인 음식·추격 대상을 잘못 정리하지 않는다. 새 콜 초기화 시 남길 월드 오브젝트와 없앨 콜 전용 Actor를 구분한다. 일시정지에는 예고·재장전·추격·연쇄 시간이 함께 멈추고, 정산·씬 종료에서는 남은 제한과 임시 객체를 정리한다.
- 현재 M 지도는 시간이 흐르지만 조작이 제한된다. 일반 차량의 정지 정책과 별개로, 신규 위험 요소에는 지도 열림 중 새 공격 시작 보류를 첫 제안으로 둔다. 이미 날아오는 물체의 피격 처리까지 포함한 지도 정책은 대표 사건 단계에서 정리하며 HTML 동작을 검토 없이 그대로 적용하지 않는다.
- 현재 기획의 '재진입마다 실행·쿨타임 없음·새 사건으로 기존 사건 대체'는 전환 대상 규칙으로 명시한다. 구현 단계에서 새 사건에 적용할 재사용·동시 실행 규칙과 함께 기준 기획서를 갱신한다. 이번에는 현행 구현 설명을 완료된 새 규칙처럼 바꾸지 않는다.

#### 4-D. 구현 순서와 확인할 결과

1. **문 1개**: 접근 감지 → 열림 예고 → 문짝 접촉. 문에서 벗어나면 맞지 않고, 헛친 뒤 정상 종료한다. 현재 주문·전달 규칙을 그대로 둔 시범 구간에서 먼저 구현 가능하다.
2. **타이어 1개**: 접근 후 구름 → 실제 접촉 → 이탈·시간 초과 종료. 평지와 경사에서 같은 방향·반대 방향 접근, 고속 통과, 지면 관통을 확인한다.
3. **맨홀 + 수박**: 접촉 발사 → 착지/미끄러짐 → 다음 위험의 2단계 연쇄. 기존 회복 처리가 후속 효과를 취소하지 않는지 확인한다. 발사·착지 상태 확장이 선행 조건이다.
4. **도난 + 일반 사고 동시 진행**: 탈취 접촉과 음식 상태 전환을 연결하고, 사고를 겪어도 추격·재수령이 유지되게 한다.
5. **콜·일차별 활성화 및 재장전**: 최소 일차 데이터와 도로 경로가 준비되면 추첨을 연결한다. 자리 수·배치 수·활성 수·행동 중 수를 구분해 확인한다.
6. **4구역·교통·고정 사건 확장**: 대표 사건 확인 후 전체 배치로 확대한다. 동시 공격 밀도, 내리막 착지, 목적지 접근 공간을 함께 조정한다.

1~2의 대표 사건 시범은 전체 맵·인라인·타이머 전환 완료를 기다리지 않고 진행할 수 있다. 현재 트래픽 시범과 같은 제한된 구간에서 확인하되, 일반 차량에 사건용 공격 행동을 섞지 않는다. 전체 도로·고도 배치도 작업은 병행 가능한 독립 작업으로 유지한다.

**사용자 플레이 확인 기준**

- 감지 영역에 들어갔다 벗어나면 문·타이어 공격을 회피할 수 있다. 경고 시간 경과만으로 강제 피격되지 않는다.
- 맞지 않은 공격은 충격·음식 분실·연쇄 기록을 만들지 않는다. 하나의 공격으로 중복 피격되지 않는다.
- 맨홀 발사 후 수박 등 다음 위험으로 이어질 수 있고, 종료 후 이동·배달을 계속할 수 있다.
- 사고·도난·차량이 겹쳐도 음식 회수 경로가 유지되고 주문·보상은 한 번만 완료된다.
- 언덕 위·아래, 수령 전·운반 중·음식 복구 중, 지도·일시정지·정산·씬 전환에서 상태와 복귀가 유지된다.
- 구현·컴파일·씬 연결·사용자 플레이 확인을 구분해 보고한다. 별도 요청 없이 Play 모드나 자동 입력 검증은 실행하지 않는다.

### 5단계: 골목·사건 배치 확장

**작업**

- 먼저 큰길 한 경로와 대체 골목 한 경로를 만든다. 건물·지름길은 기존 Map을 보존하며 에디터에서 편집한다.
- 골목은 경로를 줄이지만 통과 여유가 적고 사건 배치가 촘촘한 선택지로 구성한다. 큰길 기준 제한시간을 유지해 지름길 이득을 만든다.
- 사건 위치는 콜 경로·수령지·고객·복귀 지점과 함께 검토한다. 목적지 바로 앞에서 진행이 막히지 않게 한다.
- 단축 거리, 통과 폭, 연쇄 간격을 확인한 뒤 4구역으로 확장한다. 명지대 지도와 골목 12개는 최종 맵 확정과 별개로 취급한다.
- 사건 풀을 늘리더라도 자리 수·그날 배치 수·콜 활성 수를 구분해 관리한다. 450곳을 먼저 복제하지 않는다.

**완료 기준**: 모든 배달 지점이 연결되어 있다. 큰길과 골목을 선택할 이유가 보이고, 빠른 이동에서도 끼임·관통 없이 통과한다. 거리·밀도 수치와 실제 체감을 별도로 기록한다.

### 6단계: 일차별 고정 사건

**첫 구현 제안**: 이삿짐 트럭 1종. 이후 경찰, 채택된 경우 공룡·용암 순서.

**작업**

- 일차·경과 시간·배달 상태에 따른 사건 시작을 연결한다. 150초 시작·110~170초 길이는 시험값으로 분리한다.
- 전조 → 단계적 규모 증가 → 종료를 만든다. 트럭은 박스 → 큰 가구 → 침대와 집주인이라는 확정된 방향을 우선한다.
- 사건 목표·가구 탑승·조기 종료 보상은 채택된 범위만 추가한다. 첫판에서 목표 보상 없이도 정상 종료되어야 한다.
- 일반 사건과 동시에 실행할 수 있도록 지속 사건의 실행·정리를 분리한다. 하루 정산과 씬 종료에서 트럭·가구·가림·이동 제한을 정리한다.
- 초과 근무 중 시작 여부, 하루 마감 직후 마지막 배달이 끝났을 때 사건 종료 방식도 정의한다.
- 경찰은 추격·골목 제한·종료부터 만들고, 바리케이드·헬기·범인 목표는 순차 확장한다.
- 공룡·용암과 두 고정 사건 동시 발생은 내용 선정과 개별 사건 검증 이후에 연결한다.

**완료 기준**: 전조를 알아볼 수 있고, 사건 중 배달이 가능하다. 목표를 놓쳐도 사건은 끝나며 잔여 장애물·조작 잠김이 남지 않는다. 고정 사건 종료가 일반 사건을 잘못 해제하지 않는다.

### 7단계: 콜 상황·긴 사건 확장

**우선순위 제안**

1. 주소 오입력: 같은 구역의 새 목적지로 변경하고 지도·고객·주문 정보를 함께 갱신한다.
2. 고양이 복서·근육맨: 예고를 보고 피하는 대결, 위험과 이득이 있는 동행을 구현한다.
3. 재촉 전화·화난 사장님·진상 손님·러닝크루: 화면 가림·추격·길막을 하나씩 연결한다.
4. 채택된 콜만 추가: 칼시간·급행·심부름·걷는 손님·묶음·먹튀·가짜 수령인.

**작업**: 새 목표를 지도와 타격 판정에 일관되게 반영한다. 후보 선택 시 공개되는 조건과 문 앞에서 등장하는 상황을 구분한다. 추격 손님은 배달 고객과 수명을 분리해 다음 콜 생성 시 사라지거나 참조가 바뀌지 않게 한다. 묶음 콜도 활성 주문 한 건 안에서 목적지만 순차 진행하며 보상을 중복 지급하지 않는다.

**완료 기준**: 목표가 바뀌어도 주문이 끝까지 완료된다. 예고·대처법이 화면에서 구분되고, 실패·회피·시간 종료에 복구가 가능하다. 여러 추격·전화·콜 상황이 영업 마감과 겹쳐도 정산을 막지 않는다.

### 8단계: 인라인·생활비·빚·저장

**작업**

- 현금·빚·인라인 보유·일차·누적 기록을 진행 상태로 분리한다. 하루 수익과 누적 현금을 구분한다.
- 생활비 → 선택 구매 → 빚 전액 확인 → 다음 날 또는 엔딩 흐름을 만든다. 생활비 부족 정책은 결정된 규칙으로 적용한다.
- 인라인은 이동 속도 증가부터 시작한다. 관성은 조작 체감에 맞춰 조정하며 승하차·배달통 시스템은 추가하지 않는다.
- 인라인을 사도 제한시간 계산은 달리기 기준을 유지한다. 모든 목적지는 달리기로 접근 가능해야 한다.
- 정산 종료 시 다음 일차부터 재개할 진행을 저장한다. 정산 재표시·다음 날 버튼 반복으로 생활비·구매·상환이 중복 적용되지 않게 한다.
- 엔딩 상태와 새 게임 선택, 저장 없음·읽기 실패·버전 차이를 처리한다. 하루 도중 저장은 후순위다.

**완료 기준**: 돈이 음수가 되지 않고 부족금 처리가 정한 정책과 일치한다. 다음 날 인라인이 적용되며 재구매가 불가능하다. 재실행 후 진행이 유지되고 전액 상환은 한 번만 엔딩으로 이어진다.

### 9단계: 표현·밸런스·배포

**작업**

- 대표 배달과 사건의 동작이 안정된 뒤 로우폴리 캐릭터·건물·애니메이션을 적용한다. 공격·예고·착지·전달의 가독성을 우선한다.
- UI·효과음·해시계·아침 뉴스·집 출발·하루 종료 연출을 정리한다. 브라우저 체험판에 없는 연출은 Unity에서 별도로 만든다.
- 사람 플레이의 하루 배달 건수·지각 비율·주문 소요·복구 시간·길 선택을 기준으로 사건 빈도와 시간을 조정한다. 봇 수치를 사람 난이도 확정 근거로 사용하지 않는다.
- 빚·생활비·기본 보상·인라인 가격·사건 보상을 한 묶음으로 조정한다. 0원 상황을 채택한다면 경제에 미치는 영향도 함께 확인한다.
- 실제 병목이 확인된 부분만 생성·파괴, 물리 충돌, 렌더링을 최적화한다. 450곳 체험판을 그대로 이식하는 것을 성능 목표로 삼지 않는다.
- 실행 빌드를 만들고, 첫날부터 인라인 구매·저장 후 재개·빚 청산까지 통합 확인한다.

**완료 기준**: 채택한 콘텐츠 범위에서 처음부터 엔딩까지 진행 가능하고, 복구 불가능한 주문·중복 지급·중복 지출·저장 손실이 없다. 실제로 확인한 항목과 미검증 항목을 구분해 제공한다.

## 4. 첫 개발 묶음과 완성 범위

> 2026-10-14 갱신: 이후 실행 순서는 [구현계획 — 첫 완성판](구현계획_첫완성판.md)을 따른다. 사용자 결정에 따라 본 게임 씬을 4구역 씬으로 옮기고, 핵심 루프 전환(M1~M3)부터 착수한다. 아래 "현재 구현 순서"는 지금까지의 진행 기록이다.

### 현재 구현 순서 — 맵·트래픽·HTML식 사건 통합

사용자의 통합 개발 순서 요청과 구현 시작 지시에 따라 아래 순서를 우선한다. 아래의 기존 타이머·전달 전환 제안은 이번 첫 묶음에 포함하지 않는다.

1. 트래픽 시범의 교차로 대기 보정 + 22개 도로·고도 배치 초안 + 접촉형 문 1개.
2. 굴러오는 타이어 1종을 추가하고 문과의 연쇄를 구성한다. 접촉 회복과 도난 추격의 동시 유지부터 확인한다.
3. 교차로 평탄화·보도·가게 진입을 포함한 4구역 지형을 Unity에 만들고 주문 목적지를 연결한다. 완성한 도로에 차량 차로를 연결한다.
4. 맨홀·수박 등 상시 오브젝트와 주문별 트리거 활성화를 적용한다. 예고·한 회차 재피격 제한·종료 정리를 공통 기준으로 유지한다.
5. 일차·콜·고정 사건, 경제·저장과 표현을 선정한 범위부터 확장한다. 타이머 시작·전달 방식 등 기존 규칙과 다른 항목은 별도 확정 후 바꾼다.

진행 상태(2026-10-14): 1번 묶음의 교차로 보정·문·[도로 고도 배치도](MapLayout/README.md), 2번 묶음의 타이어·대표 연쇄에 이어, 3번의 [4구역 지형 시범](4구역_지형_구현.md)을 별도 씬에 생성·저장했다. 22개 도로·58개 평탄 영역·45개 출입 위치·기존 6개 주문·대표 큰길 두 구간의 차량 3대를 연결했다. Unity 컴파일·참조·정적 배치 확인은 완료했고 실제 플레이는 미검증이다. 새 씬의 기존 사건 복사본은 지형에 맞는 배치 전까지 비활성화했으며 기존 `TrafficPilot`에는 유지했다. 다음 묶음은 4번의 맨홀·수박 대표 사건과 새 지형 사건 배치다. 전체 교차로 교통망은 대표 구간 운행의 사용자 확인 이후 확장한다.

추가 진행(2026-10-14): 4번의 대표 오브젝트 묶음으로 L7 문·타이어, L8 도난·맨홀·수박을 새 맵에 배치했다. 착지 후 미끄러짐, 접촉 회복 수명, 추격 중 재진입 보호를 구현했다. Unity 컴파일·씬 저장·필수 참조·정적 경로 여유 확인 완료, 실제 플레이 미검증. [대표 사건 구간 구현](기록/대표_사건_구간_구현.md)에 확인 절차를 기록했다. 주문별 활성화와 일차별 사건 밀도는 아직 구현하지 않았다.

### 기존 첫 개발 묶음 제안 — 현재 순서보다 후순위

1. 수령 시 배달 타이머 시작.
2. 1번 수동 콜 확인과 콜·지도 시간 정책 분리.
3. 주먹 전달과 고객 날아감.
4. 하루 해시계와 마지막 주문 정산 유지.

기존 Map과 소수 주문으로 이 묶음부터 확인한다. 신규 대형 맵·수백 개 사건·경제를 동시에 바꾸지 않아 전달과 타이머 문제의 원인을 좁힐 수 있게 한다.

### 첫 완성판 제안

구역 순환 배달, 달리기·인라인, 해시계, 대표 오브젝트·트리거와 연쇄, 큰길·골목 선택, 트럭 고정 사건 1종, 주소 오입력, 생활비·빚·다음 날·저장·엔딩을 포함한다. 이 범위도 최종 콘텐츠 승인 목록이 아니라 전체 게임 흐름을 먼저 완성하기 위한 제안이다.

경찰·고양이·근육맨은 다음 확장 우선순위다. 공룡·용암·두 사건 동시 발생, 나머지 콜 상황, 전체 450곳 배치와 57콤보는 개별 선정과 대표 기능 검증 후 확장한다. 확장 전에도 첫 완성판에서 엔딩에 도달할 수 있게 한다.

## 5. 재사용·변경 범위

| 현재 구성 | 활용 계획 |
|---|---|
| `DeliverySession` | 단일 주문·마감·정산·중복 방지 유지. 타이머 시작과 콜 표시 변경 |
| `DeliveryOrderDefinition`·`DeliveryOrderRoute` | 음식점·고객·보상 데이터 활용. 구역과 거리 계산을 실제 필요한 범위에서 추가 |
| `RiderMotor`·`ThirdPersonCamera` | 이동·카메라 기본 활용. 공격·점프·발사·인라인 반응 확장 |
| `DeliveryResident` | 고객 식별·복귀 활용. 접촉 완료를 타격 요청으로 전환 |
| 지도·목적지·정산 UI | 위치 표시·정산 기록 활용. 콜 화면·구역·해시계·새 목표 확장 |
| `IncidentTrigger`·설정·Actor | 효과 설정과 실행 분리 활용. 활성화 조건과 지속 사건 수명 변경 |
| `IncidentDirector` | 중단·종료 정리 경험 활용. 모든 사건을 한 건으로 대체하는 제약 수정 |
| `TimedIncidentScheduler` | 새 방식 채택 시 역할 대체. 전환 전 제거하지 않음 |
| `FoodThief`·음식 복구 | 미결 정책이 정해질 때까지 복구 안전장치 유지 |
| Map 프리팹·설치 도구 | 기존 사용자 자산 보존. 씬·배치는 에디터 API로 편집 |

HTML은 동작·수치·연출 참고다. JavaScript를 Unity 코드에 그대로 복사하지 않고, 프로젝트의 물리·입력·씬 수명에 맞춰 구현한다. 기존 스크립트를 일괄 교체하거나 패키지·GUID를 임의 변경하지 않는다.

## 6. 검증과 단계 보고

- Codex: 코드·참조 검토, 필요한 최소 컴파일 오류 확인, 에디터에서의 씬 편집·저장 확인. 문서만 바뀌는 작업에서는 컴파일을 불필요하게 실행하지 않는다.
- 사용자: 실제 이동·주먹·충돌·연쇄·사건 스트레스·지도 가독성·경제 체감 확인. 별도 요청 없이 자동 플레이·Play 모드·반복 캡처를 실행하지 않는다.
- 단계 보고: 변경한 동작, 구현·컴파일·씬 적용·플레이 확인 상태, 짧은 확인 절차, 남은 문제를 제공한다.
- 수동 확인의 공통 조건: 수령 전 / 운반 중 / 음식 복구 중 / 영업 마감 직후 / 일시정지·콜 UI / 정산·씬 종료에서 규칙이 유지되는지 확인한다.
- 체감 결과가 아직 없어도 독립적인 다음 기능은 진행 가능하다. 다만 미검증 상태를 완료로 보고하거나 그 수치를 최종 밸런스로 고정하지 않는다.
