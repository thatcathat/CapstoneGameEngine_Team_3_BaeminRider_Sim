# 배달 라이더 프로토타입 제작 워크스루

- 작성일: 2026-09-18
- 기준: [프로토타입 기획서](배달라이더_프로토타입_기획서.md), [프로젝트 규칙](../project_rules.md)
- 상태: 타이틀·게임 씬 및 0~2단계의 첫 구현 작성. 전체 플레이 검증은 미완료이며 아래 계획 전체가 완료된 것은 아니다. 현재 결과와 검증 범위는 [첫 배달 실행 안내](첫_배달_실행_안내.md)를 참조한다.
- 검증 담당 변경: 이후 실제 플레이·조작감 검증은 사용자가 수행한다. 아래 플레이 확인 항목은 사용자용 체크리스트이며, Codex는 별도 요청 없이 자동 플레이·반복 캡처를 수행하지 않는다. 개발 시 코드 검토와 최소 컴파일 오류 확인만 한다.
- 후속 진행: 사용자가 첫 배달 정상 작동을 확인했다. 후속 계획 1~3번(주문 데이터 분리, 배달지 확장, 후보 3개 관리)을 구현하고 씬에 적용했다. [주문 후보 개발 안내](주문_후보_개발_안내.md) 참고. 지도 UI와 타이머는 아직 후속 작업이다.
- 후속 4~6번: 사용자가 1~3번의 정상 작동을 확인한 뒤 지도·프로필 주문 선택·목적지 안내를 구현했다. [지도·주문·목적지 안내](지도_주문_목적지_안내.md)에서 사용자 확인 절차를 제공한다. 다음 범위는 주문·하루 타이머와 보상·정산이다.
- 후속 7~8번: 사용자가 지도 단계의 정상 작동을 확인한 뒤 주문·하루 타이머, 정시·지각 보상, 마지막 주문 마무리와 하루 정산을 구현했다. [시간·보상·정산 안내](시간_보상_정산_안내.md) 참고. 플레이 검증은 사용자 담당이다.

## 제작 목표와 순서

첫 목표는 **작은 테스트 공간에서 걸어서 음식을 받고, 고객에게 부딪혀 배달 한 건을 완료하는 것**이다. 이동과 충돌 전달을 먼저 확인한 뒤 지도·시간·사건·경제를 순서대로 연결한다.

| 순서 | 제작 항목 | 이 단계에서 직접 해볼 수 있는 것 |
|---|---|---|
| 0 | 환경과 작업 씬 준비 | 전용 테스트 씬 실행 |
| 1 | 도보 이동·카메라·주민 충돌 | 걷고 시점을 돌리며 주민을 밀기 |
| 2 | 주문 한 건의 수령·전달 | 음식을 받아 고객과 충돌해 완료 |
| 3 | 지도 주문 선택 | 후보 3개 중 한 건을 선택해 수행 |
| 4 | 타이머·보상·하루 종료 | 정시·지각 배달 후 하루 정산 |
| 5 | 사고 사건 | 사고로 지연되어도 배달을 마무리 |
| 6 | 도난·음식 복구·사건 발생 제어 | 추격 회수 또는 재수령 후 전달 |
| 7 | 요청 사항·팁·리뷰 | 요청 사항 결과에 따라 팁과 리뷰 확인 |
| 8 | 관리비·빚·다음 날 | 수익과 지출을 반영해 다음 날 진행 |
| 9 | 자전거 구매·이동 | 구매 후 다음 날 더 빠르게 배달 |
| 10 | 저장·불러오기·엔딩 | 진행을 이어서 플레이하고 빚 전액 상환 |
| 11 | 시각·사운드 정리와 통합 검증 | 전체 프로토타입을 빌드로 플레이 |

기획서의 핵심 배달 검증 단계는 0~5, 완결된 반복 플레이 단계는 6~10에 해당한다. 각 단계에서 기능과 관련된 기본 UI도 함께 만든다.

## 0. 환경과 작업 씬 준비

**작업:** 대상 Unity 프로젝트 연결, 현재 씬의 저장 상태, 컴파일 오류, 입력·렌더링 설정을 확인한다. 기존 사용자 작업물을 보존하면서 `Assets/_Game/Scenes/DeliveryPrototype.unity`를 전용 작업 씬으로 만든다. 씬과 자산은 에디터 도구 또는 에디터 API로 구성한다.

바닥, 단순 건물 블록, 조명, 시작 지점, 음식점 1곳, 고객 지점 1곳을 배치한다. 필요한 폴더만 생성하고, 초기에는 색과 형태로 대상을 구분한다. UI를 만들 때는 기존 구성을 확인한 뒤 사용할 프레임워크와 한글 표시 방식을 결정한다.

**완료 기준:** 전용 씬을 열어 Play 모드에 진입할 수 있고 프로젝트 컴파일 오류가 없다. 기본 맵을 저장하고 다시 열어도 유지된다.

## 1. 도보 이동·3인칭 카메라·물리 충돌

**작업:** WASD 이동, 마우스 시점 회전, 카메라 기준 이동을 구현한다. 플레이어, 바닥, 벽, 주민의 충돌을 구성한다. 움직일 때 주민을 밀 수 있으면서 플레이어가 쉽게 전도되거나 벽을 통과하지 않도록 조정한다.

사고 반응과 자전거 확장을 고려해 물리 이동 방식을 먼저 검증한다. 초기 권장안은 회전 제약을 둔 Rigidbody 기반 이동이며, 구현 전 현재 프로젝트 구성과 적합성을 확인한다. 카메라의 벽 가림과 맵 이탈 복귀도 기본 수준으로 처리한다.

**플레이 확인:** 직진·대각선 이동, 급회전, 벽 접촉, 주민 밀기, 좁은 통로 통과, 맵 밖 추락을 확인한다.

**완료 기준:** 안정적으로 이동하고 주민과 접촉할 수 있다. 카메라가 주요 플레이를 가리지 않으며 이탈 후 복귀한다.

**사용자 피드백:** 이동 속도, 회전 감도, 카메라 거리, 주민 충돌의 느낌.

## 2. 주문 한 건의 수령·충돌 전달

**작업:** 고정된 시험 주문 한 건과 간단한 수락 버튼을 만든다. `주문 없음 → 음식 수령 전 → 배달 중 → 완료` 흐름을 구현한다. 음식점 근처에서 E로 음식을 받고, 음식 보유 표시와 현재 목표를 보여준다.

음식을 가진 채 해당 고객에게 부딪히면 완료 알림을 표시한다. 주문 상태와 완료 처리는 한 곳에서 관리한다. 이 단계의 시험 주문 UI는 3단계 지도 UI로 연결하며, 별도 주문 로직을 중복 구현하지 않는다.

**완료 기준:** 올바른 고객과 충돌하면 한 번만 완료된다. 일반 주민 충돌, 수령 전 고객 충돌, 반복 접촉은 잘못된 완료를 만들지 않는다. 밀린 고객을 마커가 따라가고 접근 불가능한 고객은 안전 지점으로 복귀한다.

**첫 시연 목표:** 사용자가 직접 주문을 받고 걸어서 수령·전달하는 짧은 플레이. 이 시점에는 시간과 경제가 아직 없어도 된다.

## 3. 지도에서 주문 선택

**작업:** 음식점·고객 위치를 소규모로 확장하고 고객 프로필 마커 3개가 있는 지도를 만든다. 프로필 선택 시 수령지·배달지·보상·제한 시간을 보여주고 수락할 수 있게 한다. 요청 사항·팁 표시는 7단계에서 연결한다.

지도에 플레이어, 음식점, 고객을 구분하고 활성 목표를 강조한다. 진행 중 다른 주문은 수락할 수 없고, 완료하면 후보를 보충한다. 지도 조작 중 커서와 이동 입력이 충돌하지 않게 한다.

**완료 기준:** 후보 중 어느 주문을 선택해도 올바른 수령지와 고객으로 연결된다. 수락 연타로 주문이 여러 개 생기지 않는다. 지도와 현장 목적지 표시가 일치한다.

## 4. 두 타이머·정시/지각 보상·하루 종료

**작업:** 하루 5분, 주문 60~120초를 초기 설정값으로 연결한다. 주문 시간은 수락 즉시 시작하며 정시 5,000원·지각 1,000원을 완료 시 한 번 지급한다. 초과 시간과 지각 상태를 HUD에 표시한다.

지도는 시간이 흐르고 일시정지는 멈추도록 한다. 하루가 끝나면 주문 수락을 막고 활성 주문만 마무리한다. 배달별 결과와 하루 수익을 보여주는 기본 정산 화면을 만든다. 정산에서 이미 받은 보상을 다시 지급하지 않는다.

**완료 기준:** 정시·지각 각각의 보상, 주문 없는 하루 종료, 수령 전·배달 중 하루 종료를 확인한다. 마감 경계에서 수락·전달이 일어나도 정산이나 보상이 중복되지 않는다.

**검증 도구:** 테스트 전용 시간 단축이나 시간 진행 기능으로 경계 상황을 빠르게 재현한다. 테스트 조작은 일반 플레이 UI와 분리한다.

## 5. 사고 사건과 회복

**작업:** 시험 구역에서 장애물 또는 단순 이동 차량과 충돌하면 밀려나고 약 2초 뒤 조작을 회복하게 한다. 사고 중에도 주문과 하루 시간이 흐르고 음식은 유지한다. 회복 안내와 간단한 충돌 피드백을 추가한다.

먼저 재현 가능한 고정 사건으로 검증하고, 6단계의 공통 발생 제어에 연결한다. 정교한 래그돌과 교통 시뮬레이션은 만들지 않는다.

**완료 기준:** 사고 후에도 현재 주문을 완료할 수 있다. 사고 중 입력으로 회복을 우회하거나 영구적으로 조작이 잠기는 문제가 없다.

**첫 핵심 플레이 완성:** 지도 주문 선택 → 수령 → 사고 대처 → 충돌 전달 → 정산.

## 6. 음식 도난과 복구·사건 발생 제어

**작업:** 음식 보유 중 도난이 발생하면 `음식 분실` 상태로 전환한다. 추격형은 도둑과 충돌하여 회수하고, 재수령형은 원래 음식점에서 다시 받는다. 도둑을 놓치거나 접근할 수 없으면 재수령으로 전환한다.

복구 안내와 목적지 표시를 연결한다. 구역 진입 확률과 일정 시간 간격의 사건 검사를 추가하고, 사고와 도난이 공통 대기시간을 사용하게 한다. 수습 중 사건 중첩, 음식 없는 도난, 고객·수령지 바로 옆 발생을 방지한다. 초과 근무에는 새 강제 사건을 시작하지 않는다.

**완료 기준:** 두 복구 방식 모두 성공하며 중복 음식 획득이 없다. 음식 분실 중 고객 접촉으로 배달할 수 없다. 분실 상태에서 하루가 끝나도 복구·전달 후 정산할 수 있다.

## 7. 요청 사항·팁·리뷰

**작업:** 첫 요청 사항으로 ‘음식 수령 후 일반 주민과 충돌하지 않기’를 추가한다. 주문 선택 화면에서 조건과 팁을 공개하고, 수행 중 성공 가능 여부를 표시한다. 완료 고객과의 전달 충돌은 실패에서 제외한다.

기본 보상과 팁을 구분해서 지급하고, 정산에 요청 사항 결과와 짧은 리뷰를 보여준다. 지각해도 요청 사항을 지켰다면 팁을 지급한다.

**완료 기준:** 요청 사항 성공·실패 각각의 팁이 정확하며 실패해도 배달은 가능하다. 정시/지각과 요청 사항 성공/실패의 네 조합이 리뷰와 금액에 반영된다.

## 8. 관리비·빚·다음 날 반복

**작업:** 정산에서 관리비 3,000원을 차감하고 부족분만 빚으로 전환한다. 시작 현금 0원, 빚 50,000원을 설정값으로 둔다. 관리비 처리 후 보유 현금 범위에서 상환할 수 있도록 한다.

다음 날 시작 시 주문, 사건, 타이머, 하루 배달 기록은 초기화하고 현금·빚·누적 기록은 유지한다. 정산을 다시 표시해도 관리비를 중복 차감하지 않는다.

**완료 기준:** 현금이 관리비보다 적거나 같거나 많은 경우를 확인한다. 현금 2,000원에서 관리비 3,000원을 내면 현금 0원·빚 1,000원 증가가 된다. 다음 날 주문과 시간이 정상 시작된다.

## 9. 자전거 구매와 이동 성장

**작업:** 관리비 처리 후 자전거를 15,000원에 구매할 수 있게 한다. 보유 여부를 유지하고 다음 날부터 자전거 이동과 간단한 외형을 적용한다. 도보의 약 1.8배 속도를 출발점으로 조정한다.

첫 버전은 별도 승하차 없이 구매한 이동 모드를 사용한다. 도보에서 검증한 수령·충돌 전달·사고·음식 복구 규칙을 공유한다.

**완료 기준:** 현금 부족 시 구매할 수 없고 이미 보유한 자전거를 중복 결제하지 않는다. 빠른 속도에서도 벽·고객을 통과하지 않으며 사고 후 조작을 회복한다.

**사용자 피드백:** 속도 증가의 체감, 회전 난이도, 골목 폭, 자전거 구매와 빚 상환의 선택.

## 10. 저장·불러오기와 엔딩

**작업:** 관리비·구매·상환을 끝내고 정산을 종료하는 시점에 현금·빚·자전거·다음 일차·누적 배달 기록을 저장한다. 다음 실행은 저장된 다음 날 시작부터 재개한다. 하루 도중 재개는 구현하지 않는다.

빚을 모두 갚으면 상환 완료와 누적 일수·배달 건수를 보여주는 엔딩으로 전환한다. 엔딩 도달 상태도 저장하여 재실행 후 이미 끝낸 게임이 잘못 이어지지 않게 한다. 새 게임 초기화는 사용자의 명시적인 선택으로 수행한다.

**완료 기준:** 저장 후 재실행해 값이 복구되고 관리비가 중복 차감되지 않는다. 저장 파일 없음·읽기 실패를 처리한다. 잔여 빚과 같은 금액을 상환하면 한 번만 엔딩으로 진입한다.

## 11. 로우폴리 표현·사운드·통합 검증

**작업:** 블록 형태로 검증한 동네에 로우폴리 건물·간판·주민·자전거를 적용한다. 목적지를 찾기 쉬운 색과 실루엣을 유지한다. 음식점·고객 프로필, 시간 경고, 수령·전달·충돌 효과음을 정리한다.

UI는 한글 표시, 화면 비율 변화, 버튼 겹침, 지도 마커 위치를 확인한다. 시각 자산 교체 후 기존 충돌 크기와 이동 경로가 깨지지 않았는지 확인한다. 마지막으로 대상 플랫폼 빌드를 만들고 에디터 외부에서 실행을 확인한다.

**통합 시나리오:** 도보 배달 → 사고·도난 복구 → 지각과 팁 결과 → 관리비 → 다음 날 → 자전거 구매·사용 → 저장 후 재개 → 빚 전액 상환.

**완료 기준:** 기획서의 프로토타입 완료 기준을 모두 확인하고, 실제 확인 결과와 남은 문제를 보고한다. 테스트 편의 기능으로 검증한 엔딩과 일반 수치로 플레이한 경제 밸런스는 구분하여 기록한다.

## 협업과 단계별 산출물

- 내가 수행할 일: 코드 작성, 에디터를 통한 씬·프리팹 구성과 연결, 최소 컴파일 오류 확인, 사용자 피드백에 따른 문제 수정.
- 사용자가 판단할 일: 이동과 충돌의 느낌, 사건 스트레스, UI 가독성, 반복 배달의 재미. 기능마다 수동 설정을 요구하지 않고 실제 플레이할 수 있는 상태로 제시한다.
- 각 단계 보고: 변경 내용, 실행 방법, 확인한 동작, 미검증 항목. 피드백 때문에 정해진 모든 단계마다 자동으로 승인을 대기하지는 않는다.
- 단계 종료 시 컴파일 확인과 사용자 플레이 검증 상태를 구분해 보고한다. 사용자 플레이 확인이 아직 없으면 미검증으로 기록하며 이를 대신 자동 실행하지 않는다.

## 현재 진행과 다음 확인

타이틀·도보 이동·주문 선택·지도·시간·보상·정산 및 구역 기반 사고는 구현됐으며 사용자가 정상 동작을 확인했다.

대화에서 정한 10~11번인 음식 도난·추격 회수·재수령, 시간 기반 사건, 종류별 및 하루 전체 발생 제한을 추가했다. GameScene 저장과 컴파일 오류 없음까지 확인했으며 플레이 검증은 사용자 확인 대기다.

설정 위치와 확인 순서는 [도난·시간 이벤트 개발 안내](도난_시간이벤트_개발_안내.md)를 따른다. 다음 기능 묶음은 요청 사항·팁·리뷰이며, 이후 관리비·빚·다음 날 진행과 자전거 구매로 이어진다.
