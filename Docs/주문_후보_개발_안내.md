# 주문 데이터·배달지·후보 관리 (1~3번)

> 사용자가 본 단계의 정상 동작을 확인했다. 이후 주문 선택 화면은 [지도·주문·목적지 안내](지도_주문_목적지_안내.md)의 지도 방식으로 확장되었다. 아래는 1~3번 구현 당시 기록이다.

## 구현 내용

- 주문 설정을 `DeliveryOrderDefinition` 자산으로 분리했다. 음식명, 음식점명, 고객명, 정시·지각 보상, 제한 시간을 Inspector에서 조정할 수 있다.
- 설정 자산은 `Assets/_Game/Settings/Orders/Order_01.asset`부터 `Order_06.asset`까지 총 6개다.
- GameScene의 DeliverySession > Order Routes에서 설정 자산과 실제 수령 위치·고객을 연결한다. 공유 설정 자산에 씬 오브젝트나 현재 진행 상태를 저장하지 않는다.
- 음식점 3곳과 고객 3명으로 초기 경로 3개 및 추가 조합 3개를 구성했다.
- 기존 주문 창 왼쪽에서 후보 3개 중 하나를 선택하고 오른쪽에서 정보 확인 후 수락한다.
- 한 건을 수락하면 활성 주문으로 옮겨지고 다른 수락은 차단된다. 음식은 선택한 음식점에서만 받을 수 있고 선택한 고객과의 충돌만 전달로 처리된다.
- 완료하면 수락하지 않았던 후보 2개를 유지하고 새 주문 1개를 추가한다. 번호는 계속 증가하며 설정 6개를 순환 사용한다.
- 중복 클릭, 진행 중 선택 변경, 잘못된 고객 전달, 완료 중복 처리를 코드에서 방지한다.

지도·M 키·프로필 마커는 아직 구현하지 않았다. 제한 시간과 금액은 정보 표시용이며 타이머 계산·보상 지급은 후속 단계다. 수락 시각은 실행 상태에 기록한다.

## 초기 주문

| 번호 | 수령 | 전달 | 음식 | 정시 / 지각 | 제한 시간 |
|---|---|---|---|---|---|
| 001 | 골목 분식 | 민트하우스 주민 | 떡볶이 세트 | 5,000 / 1,000원 | 60초 |
| 002 | 노을 도시락 | 남쪽 골목 주민 | 따뜻한 도시락 | 5,500 / 1,000원 | 90초 |
| 003 | 공원 베이커리 | 북쪽 공원 주민 | 빵과 우유 | 6,000 / 1,000원 | 120초 |

처음 001번을 완료하면 002·003번이 유지되고 004번(골목 분식 → 남쪽 골목 주민)이 추가된다. 이 수치와 후보 순서는 초기 테스트 설정이다.

## 배치

초기 카메라가 바라보는 방향을 북쪽으로 보면 골목 분식은 왼쪽 교차로, 노을 도시락은 오른쪽 남쪽 보도, 공원 베이커리는 왼쪽 북쪽 보도에 있다. 노란 원과 음식점 이름을 표시했다.

민트하우스 주민은 오른쪽 중북부, 남쪽 골목 주민은 왼쪽 남부, 북쪽 공원 주민은 오른쪽 북부에 있다. 주민 머리 위 이름으로 구분한다. 기존 건물과 첫 수령지·고객 위치는 보존했다.

## 사용자가 확인할 순서

1. TitleScene에서 Play → 배달 시작. 주문 후보가 3개인지 확인한다.
2. 각 후보를 클릭해 음식점·고객·음식·금액·제한 시간이 달라지는지 확인한다.
3. 002 또는 003번을 수락한다. HUD가 해당 음식점 이름으로 바뀌는지 확인한다.
4. 다른 음식점에서는 E로 수령되지 않고, 지정 음식점에서는 수령되는지 확인한다.
5. 일반 주민과 다른 고객에게 부딪혀도 완료되지 않는지 확인한다.
6. 지정 고객과 충돌하면 한 번만 완료되고 후보가 다시 3개가 되는지 확인한다.
7. 수락하지 않은 후보 2개가 그대로 있고 새 번호의 주문이 추가되는지 확인한다.
8. 다음 주문 수락과 일시정지·타이틀 복귀를 확인한다.

## 확인 범위

코드 검토, Unity 컴파일 실패 없음, 씬 저장, 주문 자산 6개와 수령지·고객·후보 버튼 참조를 확인했다. 이번 작업에서는 Play 실행, 입력 시뮬레이션, 캡처, 자동 플레이 검증을 수행하지 않았다.

씬 제작 호출 중 연결 도구가 5초 응답 시간 초과를 기록했지만, 생성·저장된 씬과 자산을 확인하여 작업 완료를 확인했다. 별도 Account API 경고는 에디터 계정 연결 관련 메시지다.

다음 작업은 지도·고객 프로필 마커·주문 상세 연동(4~6번)이다.
